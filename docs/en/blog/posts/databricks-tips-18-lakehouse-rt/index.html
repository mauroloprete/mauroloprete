Databricks Tips #18: Lakehouse//RT — sub-100 ms for real?

Databricks Tips
Data Engineering
Serverless
I enabled the Lakehouse Real-Time Beta in Databricks and measured it against a serverless SQL warehouse: reproducible benchmark, real costs, limits.
Author

Mauro Loprete

Published

October 24, 2026

If your application or dashboard needs answers in milliseconds, the usual pattern hurts: you stand up a separate serving system next to the lakehouse and copy the data into it. Two systems, two copies, two governance models, and a sync pipeline to maintain. At the June Data + AI Summit, Databricks announced Lakehouse//RT with a promise to kill that copy: sub-100 millisecond queries straight on your Unity Catalog tables. Instead of repeating the announcement, I enabled the Beta in my workspace and measured it properly.

NoteTL;DR
  • Lakehouse//RT (doc name: Lakehouse Real-Time) is a new type of serverless SQL warehouse, in Beta, built for SELECT queries with low latency and high concurrency. Under the hood runs a new engine called Reyden.
  • In my benchmark, the server-side median for a point lookup was 35.5 ms on RT versus 501.5 ms on serverless: 14 times faster, both warehouses Small.
  • At 1000 queries in flight RT holds medians between 30 and 286 ms depending on the query; serverless without cache climbs into seconds.
  • The same run cost US$ 9.21 on RT and US$ 22.88 on serverless: the faster engine burns fewer DBUs (Beta promo included).
  • The Beta is read-only: GRANT, OPTIMIZE and AI Functions fail with UNSUPPORTED_FEATURE. The full benchmark is reproducible from the lab on GitHub.
TipThis lab is also on video

The full benchmark running live, with the panel charting in real time: on YouTube and Spotify. And if you want to run it yourself, the lab is on GitHub: dataset, harness and panel, reproducible with databricks bundle deploy plus bundle run.

What is Lakehouse Real-Time?

It is a new type of serverless SQL warehouse that showed up as a Beta after the Summit announcement. The docs describe it for one specific job: serving read queries with sub-second latency and high concurrency, the territory currently held by the specialized serving stacks living next to the lakehouse. The engine underneath is called Reyden and, according to the press covering the keynote, the name comes from “Reynold’s Dream Engine”, after Reynold Xin, Databricks co-founder.

The architectural point: queries run directly on Unity Catalog managed tables, in Delta or Iceberg format, under the same governance. No copy, no sync pipeline, no second permissions catalog.

Warning

Everything below is a Beta: the feature set can change before general availability. The numbers in this post are my own measurements, from October 2026, in my Azure workspace. They are not Databricks’ official benchmark and do not pretend to be.

Enabling the Beta and creating the warehouse

Enabling it is a toggle in the workspace Previews page, flipped by a workspace admin. With the preview on, the SQL warehouse creation flow shows a Real-Time type next to Serverless, Pro and Classic. Two details that caught my attention:

  • The size is called Query size (Small to X-Large) and the docs put it in the main step of the form; in my workspace it only appeared after opening Advanced Options, Beta things. Autoscaling is not measured in clusters as usual: it is measured in DBUs, the compute unit Databricks bills with.
  • The API shows it is a type of its own: in my workspace databricks warehouses list reports it as warehouse_type: REALTIME, an enum that landed in the official SDKs in October 2026. Note that regular serverless warehouses report as PRO with the enable_serverless_compute flag, a classic source of confusion.

The lab: 20 million orders and three serving queries

To measure something resembling real serving I built a synthetic dataset: 20 million orders and 200 thousand customers, Unity Catalog managed tables (a Beta requirement), with Liquid Clustering on (cliente_id, ts), which is exactly how the queries arrive. Three queries any app would run:

Query What it does Pattern
Q1 Status of a single customer Lookup with clustering pruning
Q2 Top 10 products in a category, last 24 h Aggregation with a time filter
Q3 Panel by segment for one country, last 7 days Join of orders against customers

Generation is a 100-line notebook; the core is this:

CREATE TABLE pedidos
CLUSTER BY (cliente_id, ts) AS
SELECT id AS pedido_id,
       1 + CAST(rand() * 199999 AS INT) AS cliente_id,
       -- random product, category, amount and timestamp
       ...
FROM range(1, 20000000 + 1);

Both warehouses in the comparison are Small, on purpose: one Lakehouse//RT and one regular serverless.

Why does the result cache ruin your benchmark?

First trap on the road: I repeated a query on serverless and it answered instantly. Not because the engine got fast, but because the result cache returned the stored result without executing anything. And on serverless that cache does not even live in your warehouse: it is a remote, workspace-level cache that survives warehouse restarts.

There is a documented session command to turn it off (SET use_cached_result = false), but it only disables the result cache: the editor also has its own UI cache and the disk cache keeps working, so in practice you can keep seeing instant answers. For a benchmark that is not enough, so I dodge it the way any serious harness would: random parameters on every request, plus a nonce projected as a column. The local cache matches on the exact query text and the serverless remote cache on the logical plan: fresh literals plus the projection dodge both levels.

The key point is that the cache is not the villain: it is a variable you have to control. That is why the benchmark runs three series: RT, serverless dodging the cache, and a third one with the same serverless repeating the identical query, cache serving results. The result_from_cache flag the Query History API returns per statement is the audit: in my run it was 0 across the 8,228 requests of the no-cache series and 1 across the 4,104 of the cached series. Nobody cheated.

The benchmark from the outside: Statement Execution API

Editor timings are fine for intuition, but a real benchmark is measured from the outside, the way an application would hit it. The harness uses the Statement Execution API, officially supported by the Beta, and records two numbers per query:

  • client_ms: wall-clock of the full request from my machine in Montevideo. It includes network and API overhead: a baseline SELECT 1 already costs hundreds of milliseconds from here. Good for comparing engines against each other, not for validating the sub-100 claim.
  • total_time_ms from Query History: everything Databricks records per statement (compilation, execution and result delivery), without the network back to my machine. That is what I use against the announcement claim; the raw data also carries execution_time_ms if you want the engine alone.

Warm-up runs are discarded, and concurrency levels go from 1 to 1000 requests in flight. In total: 12,332 measured requests.

Results: latency

With one query at a time, the server-side distribution per query looked like this:

Three direct takeaways:

  • RT delivers sub-100 server-side on all three queries with one query in flight: medians of 35.5, 59 and 86.5 ms.
  • Serverless without cache lands between 14 and 14.3 times slower in median depending on the query.
  • The serverless cache is great when it applies (189 to 208 ms), but it only applies to deterministic queries over unchanged data, and entries live 24 hours. A real app with variable parameters almost never lives in that world.

What happens with 1000 queries in flight?

The strong promise of the announcement is not latency at one query: it is holding it under concurrency. I raised the load from 1 to 1000 simultaneous requests:

In short: RT does not just start lower, it stays lower. On the point lookup, the median at 1000 requests in flight was lower than at a single one (30 versus 35.5 ms). Serverless without cache degrades into seconds on the aggregation and join queries. And the cached series is the interesting exception: at 1000 identical requests the cache answers steadily (147 to 163 ms), because a thousand repetitions are the cache’s ideal scenario. If your real workload is “the same dashboard refreshed by a thousand people”, serverless with cache is enough; if every request carries different parameters, it is not.

Tip

Always measure both sides: client-side tells you what your user will feel (from Montevideo, network and API overhead set a floor of hundreds of milliseconds), and server-side tells you which engine is better. Comparing official claims against client-side numbers is cheating at solitaire.

What the Beta does not support (and what ran anyway)

The docs say Lakehouse//RT is read-only: standard SELECT, no writes, no DDL (the commands that create or modify objects), no GRANT or REVOKE, no OPTIMIZE and no AI Functions. I probed the limits live and the real output was this:

[UNSUPPORTED_FEATURE] Function `ai_classify` is not supported in Lakehouse//RT.
Please change your query or use a Serverless SQL Warehouse instead.
See Lakehouse//RT limitations:
https://docs.databricks.com/aws/compute/sql-warehouse/real-time#limitations
SQLSTATE: 0A000

GRANT failed with the same kind of error. But here comes the finding I did not expect: INSERT and CREATE TABLE ran without error in my workspace, against what the docs say. Do not take it as a feature: whatever works outside the docs in a Beta can be cut without notice, and the engine’s declared design is serving reads. Treat it as read-only anyway.

It also does not work today with Genie, Genie Agents or as compute for Jobs tasks, and it requires managed tables: no external tables, Hive, foreign tables or loose formats like CSV, JSON or Parquet. With custom applications it is the other way around: serving them data is precisely the use case, via drivers and the Statement Execution API.

How much does Lakehouse//RT cost?

I went to the system tables to read the fine print. Two data points from my run:

  • In my region, on the day of the run, system.billing.list_prices showed the same unit price per DBU for both SKUs (the SKU is the product line Databricks bills you under). Do not take it for granted: since 2026-10-10 RT bills under its own SKU with its own regional rate, so check yours.
  • The same battery of tests consumed 32.69 DBUs (US$ 22.88) on serverless and 13.15 DBUs (US$ 9.21) on RT: a 60% smaller bill. Note those 13.15 already include the Beta promo, which emits 30% fewer DBUs until 2027-01-31: without the promo it would be ~18.8 DBUs and the saving would be around 42%.
Important

The low cost depends on the use case: this is short-read serving, the terrain where RT shines. Do not extrapolate to transformation workloads, which the Beta cannot run anyway.

When yes, when no?

Your case What I would use
Serving analytics to an app or dashboard with high concurrency and variable parameters Lakehouse//RT
The same dashboard refreshed identically by many users Regular serverless: the result cache solves it for free
Point lookups of features for models Look at the Online Feature Store with Lakebase first
Internal BI with no sub-second requirement The serverless you already have is plenty
Writes, transformations, table maintenance Anything but RT: the Beta is read-only
Real-time stream processing That is Structured Streaming’s Real-time mode, a different product

Gotchas

  1. The serverless remote cache lives at workspace level: it survives warehouse restarts, and SET use_cached_result = false may not cut it in the editor. To compare engines, fresh parameters on every run.
  2. The local cache matches on exact text and the serverless remote cache on the logical plan: to dodge both at once, the nonce goes projected as a column, not in a comment.
  3. The API reports warehouse_type: PRO for regular serverless warehouses; RT does show up as REALTIME. If you filter by type, remember the enable_serverless_compute flag.
  4. The first request after starting the warehouse is not representative: discard warm-up runs or you will measure the startup, not the engine.
  5. result_from_cache from Query History is your audit: if your “no cache” benchmark shows hits, the numbers are worthless.
